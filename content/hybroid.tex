\chapter{Multimodal Android Malware Analysis with \hybroid{}}
\label{chap:hybroid}

\section{Research Problem and Contribution}
\label{sec:hybroid:1}

An Android package can contain code paths that a test never executes, so its traffic capture
cannot describe communication those paths might produce. Conversely, flow statistics describe
observed communication without identifying the code path that produced it. Static analysis can
recover program structure beyond the executed paths, subject to the limits described in
Section~\ref{sec:background:android:analysis}. For malware classification, the unresolved
question is whether combining these partial observations improves predictions over either
source alone on the same applications. This possible complementarity motivates \hybroid{};
its value must be measured for the chosen representations and prediction task.

This chapter addresses RQ1, stated in Section~\ref{sec:intro:rqs}: \rqOneText{}
It examines gap~\gapref{1} through a joint representation and a comparison on one application
cohort, separately for each prediction task and learner.

Program graphs supply context for the code features: control-flow edges relate basic blocks,
while call-graph edges relate methods. \hybroid{} combines learned opcode features with this
recovered structure in its static branch \cite{norouzian2021hybroid}. As introduced in
Sections~\ref{sec:background:graphs:pairwise} and~\ref{sec:background:learning:messagepassing},
graph propagation combines a block's instruction features with neighbouring block states.
The code representation is fitted using application labels for malware detection, so training
can adapt its features to that task. Its fixed-width output supplies the static input to the
final classifier.
The network branch supplies flow statistics, such as duration and byte counts, without requiring
payload contents. Both branches must describe the same application before their features can
be combined.

Figure~\ref{fig:hybroid:architecture} presents the pipeline. Each sample enters as an APK paired
with traffic recorded on a physical handset~(1); the branches process these observations in
parallel~(2). The static branch yields a 64-dimensional code vector, and the network branch
aggregates flow records into \netfeatures{} features per application. This common unit permits
feature-level fusion: concatenating the vectors gives one classifier access to both feature
groups~(3). This final supervised learner fits their associations with the target labels~(4),
with separate models for binary detection and five-class prediction into Benign or one of four
malware categories~(5). Representation learning in the code branch and final classification
thus serve distinct roles; Sections~\ref{sec:hybroid:5} to~\ref{sec:hybroid:8} define them.

  \caption{The \hybroid{} architecture, redrawn by the candidate from \cite{norouzian2021hybroid}.}
  \label{fig:hybroid:architecture}

The contribution comprises this multimodal pipeline and its within-system evaluation.
Section~\ref{sec:hybroid:11} compares the joint input with each branch alone for the same learner
and task. The reported mean $F_1$ gains over the better single modality are one or two percentage
points for detection; category-classification differences range from minus two to plus three
points, depending on the learner. These descriptive results support a task-dependent benefit
from fusion. The evaluation leaves the relative merits of alternative fusion mechanisms open.

The work was published at ISC 2021 \cite{norouzian2021hybroid}. The candidate is the first of four
authors, with shared first authorship recorded for the first two. He designed the overall pipeline
and its network-traffic analysis, together with the framework used for preprocessing and
evaluation. He conducted the experiments and wrote the manuscript. His contribution to graph
processing was partial, as stated in Section~\ref{sec:intro:publications}.

\section{Related Work}
\label{sec:hybroid:2}

Static Android detectors use features available in the application package. DREBIN combines
manifest declarations with features extracted from bytecode, including API calls and network
addresses, in a sparse representation classified by a linear model \cite{arp2014drebin}.
It is one of the baselines in Section~\ref{sec:hybroid:9}. API-level detectors include
DroidAPIMiner \cite{aafer2013droidapiminer}, while other approaches combine permissions and API
calls \cite{peiravian2013machine}. Factorisation machines and static behaviour classifiers also
use manifest and API feature vectors \cite{li2019android, chen2018android}.

Opcode-based methods describe instructions at a lower level. Canfora et al.\ evaluate opcode
$n$-grams for malware detection \cite{canfora2015effectiveness}; McLaughlin et al.\ train
convolutional networks on opcode sequences \cite{mclaughlin2017deep}. \hybroid{} uses opcode
embeddings as features within a structured program representation. Basic blocks and their
control-flow relations provide the intermediate units described in Sections~\ref{sec:hybroid:5}
and~\ref{sec:hybroid:6}.

Graph-based methods differ in both the relations they encode and their vertex features. Adagio
maps neighbourhoods of a function-call graph to features for a linear classifier and permits
the associated code structures to be inspected \cite{gascon2013structural}. apk2vec learns
application representations from several graph views \cite{narayanan2018apk2vec}. MaMaDroid
models transitions between abstracted API calls as Markov chains; package- or family-level
abstraction reduces dependence on individual method identities \cite{onwuzurike2019mamadroid}.
Attributed control-flow graphs have also been used for binary-code similarity and malware
classification \cite{xu2017neural, yan2019classifying}. These methods operate at different
program granularities, as defined in Section~\ref{sec:background:graphs:pairwise}. This distinction
guides the static design in \hybroid{}: opcode embeddings describe block contents, and graph
propagation incorporates neighbouring blocks. The rationale is to use instruction information
together with structural context; the modality comparison evaluates that code branch as a whole.

The choice of vertex features remains relevant in later work. Tran et al.\ augment function-call
graphs with function metadata and code embeddings, and report improved classification under
distribution shift relative to topology-based features \cite{tran2025quantifying}. Their
MalNet-derived benchmarks provide evidence for that comparison, rather than a validation of
\hybroid{}'s opcode representation. A broader survey describes the extraction and learning
choices used in graph-based malware detection \cite{bilot2024survey}.

Dynamic network analysis measures communication during execution. Arora et al.\ use traffic
statistics with a rule-based classifier, and Zulkifli et al.\ evaluate a decision tree on network
features \cite{arora2014malware, zulkifli2018android}. CREDROID examines network activity,
including transmitted information \cite{malik2016credroid}. In the broader malware-traffic
literature, learned representations operate on raw packets or sessions
\cite{marin2021deepmal, wang2017malware}. The observation unit determines which traffic is
represented together and what a prediction label describes. Application-level aggregation in
\hybroid{} permits fusion with the code vector, at the cost of the record order and variation
discarded by averaging (Section~\ref{sec:hybroid:7}).

The CICAndMal2017 study classifies Android malware from flow features and provides the dynamic
baseline used here \cite{lashkari2018toward}. A later extension combines network-flow and API
features \cite{taheri2019extensible}. Hybrid methods cover a wider range of observation pairs
and fusion mechanisms \cite{jain2026hybrid}. MARVIN compares static, dynamic and combined
features, while the study by Onwuzurike et al.\ compares the modalities through a common
behavioural model \cite{lindorfer2015marvin, onwuzurike2018family}. Both report advantages for
the combination in their evaluated settings. These studies establish precedents for hybrid
analysis; the observation pair and fusion mechanism determine the design examined in each case.

HGDetector later combines static network-related call-graph features with graphs derived from
network traffic \cite{feng2025hgdetector}. Its experiments use CICAndMal2017 and a filtered
CICMalDroid2020 corpus, with gains that depend on the available traffic. This supports examining
fusion under explicit observation conditions. Its reported gains are not directly comparable
with Hybroid's because the representations and evaluation cohorts differ.

The earlier hybrid studies do not establish whether adding a learned program-graph vector to
application-level flow statistics improves classification for the tasks and cohort studied here.
RQ1 tests
that particular combination against each feature group alone on the same application cohort
and with the same learner type. Binary detection and category classification require separate
comparisons because their labels distinguish applications in different ways. The observation
requirements and evaluation protocol are specified next.

\section{Observation and Threat Model}
\label{sec:hybroid:3}

The static observation is the Dalvik bytecode recovered from the APK, including its methods and
call sites. The dynamic observation is the packet capture associated with an application's
execution on a physical handset. Argus converts that capture into bidirectional flow records.
The classifier receives features derived from both observations after acquisition and
preprocessing \cite{norouzian2021hybroid}.

This design supports offline application analysis when an APK and a corresponding traffic
capture are available. In the reported evaluation, those inputs were supplied by CICAndMal2017;
the candidate's pipeline processed the recorded traffic. A new application would likewise
require a capture before the fused classifier could be used. Chapter~\ref{chap:hgann}
examines a different observation requirement: analysis from the application package alone.

The static branch covers the bytecode visible to its analyser. Behaviour implemented in native
libraries or code loaded during execution can be absent from that representation. The dynamic
branch records network activity during the capture window, which may include consequences of
such behaviour, but it supplies neither system-call traces nor decrypted payload contents.
It therefore provides evidence about the observed execution rather than all possible executions.

The evaluation is non-adaptive: the malware samples were collected before the detector was
developed, and no attacker modifies an application in response to its predictions. Attacker
knowledge and perturbation budgets are not specified. The results consequently concern
classification of the collected samples, with adversarial robustness remaining a separate
evaluation question.

messaging and social platforms. The capture scenarios cover installation and periods before

comparison of static and dynamic representations required by RQ1.

\section{Opcode and Basic-Block Representation}
\label{sec:hybroid:5}

Dalvik instructions encode an operation and its operands. Operand fields may identify registers,
contain literal values or reference other DEX items, such as methods and strings
\cite{aosp2026dalvikbytecode}. \hybroid{} retains the opcode and omits these operand fields.
This abstraction limits the vocabulary to the 216 opcode types used in the study, at the cost
of information about the values and objects on which each operation acts.

The opcode vectors are learned with the skip-gram formulation of word2vec
\cite{mikolov2013distributed}. The training corpus contains 18,240,542 opcode occurrences
extracted from AndroZoo applications \cite{norouzian2021hybroid}. For a sequence
$o_1,\ldots,o_L$ over a vocabulary $\mathcal O$, let $\mathcal C_t$ contain the positions within
a context window of $o_t$, excluding $t$ itself. The canonical objective is
\begin{equation}
  \begin{aligned}
    \max_{\theta}\quad &\frac{1}{L}\sum_{t=1}^{L}
      \sum_{j\in\mathcal C_t}\log p_{\theta}(o_j\mid o_t),\\
    p_{\theta}(o'\mid o) &=
      \frac{\exp(u_{o'}^{\mathsf T}v_o)}
           {\sum_{r\in\mathcal O}\exp(u_r^{\mathsf T}v_o)}.
  \end{aligned}
  \label{eq:hybroid:skipgram}
\end{equation}
Here $v_o,u_o\in\mathbb R^l$ are the input and output embeddings, and $\theta$ contains their
parameters. The objective rewards prediction of local opcode contexts. It defines the learning
aim; the Hybroid publication does not specify which training approximation was used.

\begin{figure}
  \centering
  \includegraphics[width=0.72\linewidth]{hybroid-opcode-powerlaw.pdf}
  \caption{Opcode frequency across the pre-training corpus. The upper panel names the twenty most
  common operations, and the lower panel plots all 216 in rank order. The figure describes
  empirical frequencies, without a statistical test of a power-law fit. Reproduced from
  \cite{norouzian2021hybroid}.}
  \label{fig:hybroid:powerlaw}
\end{figure}

Figure~\ref{fig:hybroid:powerlaw} shows that opcode frequencies are uneven. Skip-gram uses
contextual co-occurrence and does not require a power-law distribution. A learned lookup table
can be reused for applications whose opcode types it covers, although vocabulary coverage alone
does not establish generalisation to new applications or independence of the evaluation data.

Operand removal also makes calls with the same opcode share a token embedding regardless of
their callee \cite{haq2021survey}. Call targets can still contribute to graph construction through
their operand references. Thus, the token features and graph edges retain different information
from the same bytecode; omitting operands from the former does not imply independence of the two.

Basic-block features provide the input to the method-level CFG encoder. The publication
describes them as weighted means of opcode vectors \cite{norouzian2021hybroid}. For a block
$b$ with opcode positions $I_b$, this design can be written as
$x_b=\sum_{j\in I_b}w_{bj}v_{o_j}/\sum_{j\in I_b}w_{bj}$, with $w_{bj}\geq0$ and
$\sum_{j\in I_b}w_{bj}>0$. The result lies in $\mathbb R^l$. This notation expresses the stated
block-level design: the source uses function-level indexing in its formula and does not specify
the weighting rule, so the exact aggregation procedure remains under-specified.

\section{Program-Graph Representation}
\label{sec:hybroid:6}

The static branch uses Androguard to extract bytecode and program graphs
\cite{desnos2012android, norouzian2021hybroid}. A method's control-flow graph describes
relations between its basic blocks. An application-level function-call graph instead relates
methods through their call sites. The published design places opcode-derived features within
this hierarchy and produces a 64-dimensional application vector
(Figure~\ref{fig:hybroid:code2vec}). The equations below define its documented method-level
encoder; the application-level composition is discussed separately.

\begin{figure}
  \centering
  \includegraphics[width=\linewidth]{hybroid-code2vec.pdf}
  \caption{Published design of the program-code branch, redrawn by the candidate from
  \cite{norouzian2021hybroid}.}
  \label{fig:hybroid:code2vec}
\end{figure}

Static graph recovery depends on the analyser and its treatment of Android execution
(Section~\ref{sec:background:graphs:pairwise}). It can include infeasible calls and omit calls
whose targets are unresolved, for example through reflection or runtime-loaded code. The
representation therefore describes recovered structure, with coverage bounded by the analysis.

Hybroid adapts structure2vec to propagate information between neighbouring basic blocks
\cite{dai2016discriminative, norouzian2021hybroid}. Let $G_f=(V_f,E_f)$ be the CFG of method $f$,
with block features $x_v\in\mathbb R^l$. Each vertex has a hidden state
$\mu_v^{(t)}\in\mathbb R^p$, and $N_f(v)$ denotes its neighbour set for propagation.
The Hybroid algorithm initialises these states at random and updates them for $T$ rounds:
%
\begin{equation}
  \mu_v^{(t+1)} = F\!\left(x_v, \sum_{u \in N_f(v)} \mu_u^{(t)}\right), \qquad v \in V_f,
  \label{eq:hybroid:meanfield}
\end{equation}
%
The update function is
%
\begin{equation}
  F\!\left(x_v, \sum_{u \in N_f(v)} \mu_u^{(t)}\right)
  = \tanh\!\left(W_1 x_v + \sigma\!\left(\sum_{u \in N_f(v)} \mu_u^{(t)}\right)\right),
  \label{eq:hybroid:update}
\end{equation}
%
where $W_1\in\mathbb R^{p\times l}$ is trainable and
$\sigma:\mathbb R^p\rightarrow\mathbb R^p$ is a fully connected network. For $k$ compatible
trainable weight matrices, its stated form is
%
\begin{equation}
  \sigma(h) = P_1\,\mathrm{ReLU}\!\left(P_2 \cdots \mathrm{ReLU}(P_k h)\right).
  \label{eq:hybroid:sigma}
\end{equation}
%
After propagation, the readout in the publication's Algorithm~1 averages the block states and
applies a linear transformation \cite{norouzian2021hybroid}:
\begin{equation}
  h_f = W_2\left(\frac{1}{|V_f|}\sum_{v\in V_f}\mu_v^{(T)}\right),
  \qquad W_2\in\mathbb R^{d_m\times p},\quad |V_f|>0.
  \label{eq:hybroid:readout}
\end{equation}
The resulting $h_f\in\mathbb R^{d_m}$ represents one method. Its hidden states depend on
information propagated through at most $T$ edges of the chosen neighbour relation. For $T\geq1$,
$\tanh$ bounds each state coordinate between $-1$ and $1$, the coordinatewise mean remains
in that interval regardless of the number of basic blocks. This controls the direct size
dependence of the pooled values without guaranteeing that different graphs remain distinguishable.

The published design subsequently forms a 64-dimensional application representation from the
method information and call structure. Its composition operator is not specified, so
Equation~\ref{eq:hybroid:readout} should not be read as an application-level pooling rule.
The symbol $d_m$ denotes the unreported method-vector dimension. The encoder can be applied
to new graphs with compatible inputs; that architectural
property alone does not establish how training and test applications were separated during
representation learning.

\section{Network-Flow Representation}
\label{sec:hybroid:7}

\begin{figure}
  \centering
  \includegraphics[width=\linewidth]{hybroid-dynamic.pdf}
  \caption{The network branch, redrawn by the candidate from \cite{norouzian2021hybroid}.}
  \label{fig:hybroid:dynamic}
\end{figure}

Argus produces bidirectional flow records from each capture \cite{qosient2026argus}. Records
are identified through source and destination addresses and ports, together with the transport
protocol, and contain roughly forty statistics. Transaction direction and state flags are
categorical and are one-hot encoded; the remaining fields are numeric
\cite{norouzian2021hybroid}.

Let $r_{ij}\in\mathbb R^q$ denote the encoded feature vector for flow record $j$ in the capture
associated with application $i$, where $q$ is the dimension after categorical encoding.
For $m_i$ records, the application-level mean is
\begin{equation}
  \bar r_i = \frac{1}{m_i}\sum_{j=1}^{m_i}r_{ij},\qquad m_i>0.
  \label{eq:hybroid:flowmean}
\end{equation}
This expresses the aggregation described in the publication \cite{norouzian2021hybroid}.
The label applies to the application and its capture; individual flows are not assigned the
application's label as separate training samples. For a one-hot indicator, the mean gives the
fraction of records with that category. For a byte-count field, it gives mean bytes per record,
not the total volume of the capture.

Reordering the extracted records leaves Equation~\ref{eq:hybroid:flowmean} unchanged because
addition is commutative. Record order and deviations from the mean are not encoded separately,
although means of temporal fields such as duration are retained. Traffic associated with malicious
activity may also be averaged together with background traffic in the same capture.

The averaged features are then min-max scaled \cite{norouzian2021hybroid}. For feature $k$,
let $\mathcal I_{\mathrm{fit}}$ denote the applications used to fit the scaling bounds:
\begin{equation}
  \begin{aligned}
    \tilde r_{ik} &= \frac{\bar r_{ik}-a_k}{b_k-a_k},\qquad b_k>a_k,\\
    a_k &= \min_{i\in\mathcal I_{\mathrm{fit}}}\bar r_{ik},\qquad
    b_k = \max_{i\in\mathcal I_{\mathrm{fit}}}\bar r_{ik}.
  \end{aligned}
  \label{eq:hybroid:flowscaling}
\end{equation}
The fitted range maps to $[0,1]$; values outside that range can map outside the interval.
Leakage-controlled cross-validation requires fitting the bounds and data-dependent feature
selection within each training fold. The publication describes these operations but does not
locate their fitting within the cross-validation procedure.

\section{Multimodal Fusion and Classification}
\label{sec:hybroid:8}

Representation learning and final classification have distinct roles. Within the static branch,
a two-layer fully connected network is trained for binary detection, with labels $+1$ for
malicious applications and $-1$ for benign applications, and a decision threshold of zero
\cite{norouzian2021hybroid}. This supervised stage fits the code representation. Its reported
output for subsequent classification is a 64-dimensional application vector.

For application $i$, denote the static vector by $s_i\in\mathbb R^{64}$ and the selected
flow features by $d_i\in\mathbb R^{13}$. Both feature groups form the joint input to the final
classifier. This is feature-level fusion: the learner receives both observations, rather than
predictions made by separate modality-specific classifiers. The 77 input features need not
contribute equally, and their counts do not establish which modality influences the decision.

The final learner is trained separately for binary detection and five-class categorisation.
The binary-trained static representation is used for both tasks; a category-specific refitting
of that representation is not reported. The experiment therefore evaluates the available
representation on each task, without isolating the effect of its binary training objective.

The reported comparisons cover a decision tree, random forest and gradient boosting
\cite{norouzian2021hybroid}. Support vector machines and naive Bayes were excluded after
preliminary tests. A decision tree partitions the feature space through axis-aligned splits;
a random forest combines predictions from multiple trees. Gradient boosting constructs an
additive model through sequential tree fits. These are different learning procedures, not a
controlled ordering of model capacity. Each is evaluated with static features, flow features
and their joint input in Sections~\ref{sec:hybroid:9} to~\ref{sec:hybroid:11}.

The missing averaging convention can be illustrated through a confusion-matrix identity.
For one binary test set of $N$ applications, let $\pi$ be the malware proportion, with precision
$P$ and recall $R$ defined for malware as the positive class. The false-negative and
false-positive counts satisfy $\mathrm{FN}/N=\pi(1-R)$ and
$\mathrm{FP}/N=\pi R(1-P)/P$, so accuracy satisfies
\begin{equation}
  \mathrm{Acc}=1-\pi\left[(1-R)+\frac{R(1-P)}{P}\right],\qquad P>0.
  \label{eq:hybroid:metricidentity}
\end{equation}
Treating Hybroid's reported accuracy, precision and recall of 0.970 as values from one such
matrix would imply $\pi=0.50$. The evaluated malware proportion is instead between 18.2\% and
20.5\%, depending on the labels of the excluded applications. This illustrates why the
reported row cannot be interpreted as a pooled malware-class confusion matrix. Class-averaged
metrics have different meanings, and separately averaged fold metrics need not satisfy the
nonlinear identity in Equation~\ref{eq:hybroid:metricidentity}. The publication supplies neither
the class-averaging definition nor raw predictions for a reconstruction. The table therefore
retains the published scores without assigning an unreported convention to them.

\section{Modality Comparison}
\label{sec:hybroid:11}

The second part of RQ1 is evaluated through the within-system contrasts in
Figures~\ref{fig:hybroid:detection-classifiers} and~\ref{fig:hybroid:categorisation-classifiers}
\cite{norouzian2021hybroid}. For a fixed learner and task, let $\overline M_s$, $\overline M_d$
and $\overline M_f$ be the reported mean scores for static, dynamic and fused inputs. The
contrast against the better single modality is
\begin{equation}
  \Delta_M = \overline M_f-\max\!\left(\overline M_s,\overline M_d\right).
  \label{eq:hybroid:fusiongain}
\end{equation}
Positive values favour fusion. Table~\ref{tab:hybroid:fusion-effects} applies this definition
to the published two-decimal means, separately for each metric.

The single-modality ordering changes with the task. Network flow has the higher reported $F_1$
for detection under all three learners: 0.90 against 0.89, 0.94 against 0.93, and 0.95 against

\cite{norouzian2021hybroid}.

Fusion adds one or two percentage points of $F_1$ in binary detection. For categorisation,
the contrast is minus two points for the decision tree, plus one for random forest and plus
three for gradient boosting. For example, gradient boosting improves from the better
single-modality score of 0.91 to 0.94 on that task. These comparisons support a modest reported
fusion benefit for detection and a learner-dependent result for category classification
\cite{norouzian2021hybroid}.

Fold-level scores and raw predictions are unavailable, so uncertainty and paired statistical
tests cannot be reconstructed. The contrasts are differences between rounded reported means,
not estimates of a statistically established improvement \cite{norouzian2021hybroid}.

\section{Limitations and Threats to Validity}
\label{sec:hybroid:12}

\paragraph{Observation conditions and temporal validity.}
The traffic describes the configured execution windows, so behaviour that was not triggered may
be absent. Its age also limits transfer to current applications. For applications targeting
Android~9 (API level~28) or higher, cleartext traffic is disabled by default, although an
application can opt in \cite{aosp2026networksecurity}. Flow statistics remain observable with
encrypted payloads, but their distribution may change with the protocol mix. Neither the main
cross-validation experiment nor the larger static-only experiment enforces temporal ordering.
Their results therefore do not establish prospective performance on later applications
\cite{pendlebury2019tesseract}.

\paragraph{Capture-related feature associations.}
Some flow fields may reflect endpoints or capture conditions as well as application activity.
An audit of UNSW-NB15 found that TTL features could distinguish operating-system populations
associated with benign and malicious traffic \cite{flood2024bad}. That finding concerns a
different corpus, but it identifies a mechanism relevant to the fields retained here.
An ablation of TTL, TOS and TCP sequence features would assess reliance on those fields and
whether their associations persist under changed capture conditions. No such test is reported
for \hybroid{}.

\paragraph{Processing coverage and obfuscation.}
The common-cohort comparison is conditional on successful extraction of both representations.
The excluded graph-extraction failures are attributed to obfuscated applications in the source
\cite{norouzian2021hybroid}. Excluding them from both branches permits comparison on the same
samples, but does not measure how a dynamic-only fallback would perform on those applications.
Identifier renaming can preserve call relations, while packing or structural rewriting can
affect recovery. The study does not establish resistance across these transformations.

\paragraph{Reproducibility and interpretation.}
The block aggregation and application-level composition remain under-specified
(Sections~\ref{sec:hybroid:5} and~\ref{sec:hybroid:6}). The recorded protocol also does not
fully document the fitting boundaries for feature preparation and model selection. A common
cohort does not by itself establish identical fold assignments or independence of every fitted
stage from test data. These are limits of the available specification, not evidence that leakage
occurred. Interpretation of the scores remains subject to the metric definitions discussed in
Section~\ref{sec:hybroid:9} and the uncertainty limits in Section~\ref{sec:hybroid:11}.

\paragraph{Adversarial evaluation.}
A relevant robustness test would apply functionality-preserving APK transformations to the
complete pipeline. Published attacks provide operators for modifying function-call graphs
\cite{song2026fcghunter, li2025efficient}. Inserted unreachable calls need not add network
communication, but functionally equivalent applications may still differ in timing-dependent
flow features. Hybroid's resilience therefore requires measurement of both branches and their
joint classifier under a specified attacker model.

\section{Chapter Summary}
\label{sec:hybroid:13}

\hybroid{} answers the first part of RQ1 with an application-level joint representation.
A learned 64-dimensional vector of static program structure is concatenated with
\netfeatures{} features averaged over the recorded network flows of the same application.
The joint input supports separate binary and five-class prediction tasks. On CICAndMal2017,
gradient boosting with this input achieves a reported detection accuracy of 97.0\% and
category classification precision, recall and $F_1$ of 0.94 \cite{norouzian2021hybroid}.

The within-system comparisons answer the second part for the evaluated cohort. Fusion improves reported
detection $F_1$ by one or two percentage points over the better single modality. Its category
classification contrast ranges from minus two to plus three points across learners. Flow
features lead code features in detection, while code features lead in categorisation for each
reported learner. These are descriptive point differences under the published protocol
\cite{norouzian2021hybroid}.

Chapter~\ref{chap:hgann} examines contextual representation within the application package
alone. Its hypergraphs encode relations among groups of methods, with no runtime traffic
capture required by the analysis pipeline.
